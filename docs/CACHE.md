# 缓存：让稳定内容得到更多复用

[首页](../README.md) · [使用指南](GUIDE.md) · [网关说明](../rikkahub_gateway/README.md)

ST 的缓存优化调整“记忆放在请求的哪里”。稳定的自我内容与本轮变化的记忆分别安排，让新增回忆出现时，前面可重复利用的内容尽量保持一致。

`tail-context-v2` 已在开发者长期自用测试中使用，并得到使用者关于缓存命中改善的明确反馈。这里记录机制与观察，不提供未经统计的提升比例或节费承诺。实际命中仍以所用模型服务回传的数据为准。

## 当前支持三种布局

环境变量：`STBRAIN_GATEWAY_CONTEXT_LAYOUT`。

| 值 | 请求布局 | 适用说明 |
| --- | --- | --- |
| `legacy` | 一份 ST 上下文在客户端消息之前 | 源码默认值，保留旧布局 |
| `anchored-v1` | 稳定帧在前，动态帧在首轮当前人类消息之前 | 严格冻结并校验首轮客户端历史边界 |
| `tail-context-v2` | 稳定帧在前，动态帧在本次客户端消息全部之后 | 本轮 ST 帧冻结，动态记忆移至尾部 |

三个值拼写精确匹配。新 `.env.example` 已选择 v2；旧配置省略变量时继续使用 `legacy`。启用 v2 时设置：

```dotenv
STBRAIN_GATEWAY_CONTEXT_LAYOUT=tail-context-v2
```

调整配置前先结束当前工具链；重启后从一条新的用户消息验证。新配置与既有工具续轮的切换分别处理。

## v2 做了什么

网关与控制面使用 `stbrain-context-layout/2` 协商带绑定和哈希的上下文包。稳定帧位于前面；本轮动态帧位于客户端本次提交的消息之后，包括该次请求已有的工具结果之后。

同一真实用户轮的工具续轮复用 ST 快照。v2 固定并认证 ST 自己的帧，不套用 v1 对整个客户端历史的逐字冻结条件；客户端当前实际提交的文本仍按原内容传递。原生工具的目录、参数、调用 ID、执行绑定和结果血缘检查继续保留。

因此，v2 改善的是注入位置和可复用前缀，同时照顾客户端在续轮重新展开动态信息的情况。它不修改 AI 保存的记忆，也不以改写旧对话来制造缓存命中。

## 客户端与偏好变化

工具目录、前端系统提示、模型参数和历史内容的变化都可能影响上游缓存。保持同一工具链所需的原生调用与结果结构，按宿主实际协议验证兼容性。

L25 的存入前提醒是工具目录描述快照。偏好不变时，投影不添加时间戳或历史计数；AI 改写或关闭提醒后，刷新出的描述确实会变化，可能影响下一次模型请求的前缀缓存。最新管理结果优先，客户端需要刷新 MCP 目录才能取得新快照。

## 怎样看效果

- 查看供应商返回的输入、缓存命中输入、未命中输入和输出用量；缺失值标为未知。
- 汇总命中率用“总命中输入 ÷ 总输入”，同时记录模型、时间段和输入规模。
- 将普通用户轮、工具续轮和连接测试分别统计，费用按实际模型账单核对。
- 稳定前缀的合成测试验证布局正确性，真实用量验证供应商实际命中；两者分别记录。

网关可记录受控用量计数、阶段和安全失败类型，帮助观察变化。公开反馈使用脱敏汇总，原文、记忆、工具参数与凭证留在受控环境。

## 升级与数据

布局选择本身不是删除记忆或恢复旧库的操作。升级来自不同旧版本时，应按实际数据库 Schema 做兼容检查、备份与恢复验证；不能将历史版本曾有的迁移项当成本次每台机器都需要重新执行的迁移。

配置、源码、三库备份与回滚步骤见 [OPERATIONS](OPERATIONS.md)。当前发布的实际验证范围见 [UPDATE-VALIDATION](UPDATE-VALIDATION.md)。
