# ST 缓存命中率排查与修复经验

[缓存机制概览](CACHE.md) · [完整指南](GUIDE.md) · [启动与备份](OPERATIONS.md) · [Linux 服务维护](LINUX-SERVICE-MAINTENANCE.md)

本文适合以下情况：同一长窗口直连表现正常，经过 ST 网关后命中偏低；某些轮次接近全命中，另一些突然很低；客户端显示的缓存数字与费用感觉对不上；不知道新配置是否真正生效。

**先给结论：使用配套版本的 `tail-context-v2`，核对实际生效布局，再看连续请求的真实 usage。不要为了命中率删除记忆、改写历史、关闭工具授权，或要求自己只能聊同一个话题。** v2 改善一个确定的请求布局问题，不保证任何模型、客户端和窗口都达到固定命中率。

本文不要求提供 API Key、私聊、人格正文、数据库或完整请求体。排查时先用本机日志的有限字段；确实需要请求对照时，优先使用合成内容。

适用基线：公版 **0.2.0-preview.5**。本文在 2026-10-10 补充实战流程与后续反馈；这是文档更新，不代表发布了新的运行时补丁。只连接 ST 的 MCP、没有经过 ST 网关时，本文的布局开关不会控制前端向模型发送的请求。

## 0. 不熟悉技术时先按这个顺序看

缓存可以理解为模型服务对“前面已经读过的内容”省下一部分重复处理。我们能改善发过去的排列方式，不能命令供应商每次都命中。

1. **先确认数字是什么。** 打开单条回复的用量，找“输入”和“缓存命中输入”，不要看窗口容量百分比，也不要问模型凭感觉估计。字段没有就记“未知”，见第 4 节。
2. **确认确实经过 ST 网关。** 记下 ST / 前端版本、实际模型和启动方式；只有 MCP 接入的用户先查前端的请求构造，不必找网关布局变量。
3. **核对正在运行的布局。** 旧安装可能仍是 `legacy`。配套升级并启用 `tail-context-v2` 后，还要在一次新请求的日志里看到 `stbrain-context-layout/2`，具体操作见第 3 节。
4. **分清偶发还是持续。** 优先查看已有的连续 3–5 次正常用量，区分普通回复与工具续轮。第一轮低、后面恢复，与每轮都只命中一点点，不是同一个问题。不为凑样本反复发送几十万 token。
5. **按现象只查一条线。** 从第 7 节选最像的一行，一次只改一个条件。已确认 v2 生效的人不要反复重启、重装；前部确实稳定的人继续看第 8 节的角色兼容反馈。
6. **修后用相同口径复核。** 既要看命中，也要看消息完整、工具正常、费用与耗时。无法闭合就用第 9 节模板反馈，不靠删库、删除旧聊天或关闭记忆来“刷高比例”。

阅读路线：先看第 2 节了解我们修过什么；第 3–6 节一步步排查；第 7 节按症状找办法；第 8 节专门说明“已经用 v2 还是低”的案例。

## 1. 先分清四种容易混淆的指标

| 名称 | 表示什么 | 不表示什么 |
| --- | --- | --- |
| 供应商上下文缓存命中 | 本次输入中有多少 token 由供应商复用 | AI 记住了多少事情、上下文窗口用了多少 |
| 输入占上下文容量的比例 | 当前输入相对于模型窗口容量的大小 | 缓存命中率、记忆正确率 |
| ST 短期记忆交接 | 可靠换窗后，把己方最近的有效 AI 正文交给新窗口参考 | 供应商 KV 缓存、所有聊天全文同步、永久存档 |
| 记忆召回、情绪连带命中 | 本轮是否找到了合适的记忆候选并按规则带入 | 供应商复用了多少输入 token |

例如，客户端右上角显示“1M / 74%”，通常是在表达窗口容量与输入规模。不能把 74% 当作缓存命中率；要查看该条回复的真实用量记录，确认 UI 对各字段的定义。

ST 当前短期交接是有界、易失的：使用可靠客户端/窗口标识，在已认证的 owner/model 范围内保留最近至多三条有效最终正文，默认有效期至多 30 分钟。同窗不会每轮重放，交接读取也不会把正文有效期无限延长。重启、关闭相应注入策略、来源不可靠或过期都可能使其不可用。这与供应商是否保留某段输入前缀是两件事。

模型能回答先前内容，不证明本次缓存命中；缓存命中很高，也不证明发生了 ST 换窗交接。思考或正文自述“我看到了注入”，不能代替实际请求与回执证据。

## 2. 我们遇到过什么，最终采用了什么

### 2.1 旧布局的确定问题

`legacy` 把稳定自我与当轮动态召回合成一份 ST 上下文，放在客户端全部消息之前。当动态资料随查询变化时，长历史之前的内容就可能变化，过早打断可复用前缀。

这是一项确定的结构性风险，但不能据此认定每一次低命中都来自 ST。前端系统提示、工具目录、历史处理、模型路由和供应商缓存状态也需要分别核对。

### 2.2 早期 `anchored-v1` 的兼容性教训

v1 将动态帧移到当前人类消息之前，并严格固定本轮初始客户端历史。有些客户端在每个工具步骤重新展开占位符、合并工具消息或重建输入。例如，开头的电量从 60% 变为 59%，就可能触发历史不匹配的 409。

不能为了绕过检查，把客户端提交的新值偷偷改回旧值；也不能认定所有时间、电量或状态信息都是可删除的“噪声”。这些可能是用户确实要求模型看到的事实。

### 2.3 当前方案：`tail-context-v2`

基础布局为：

```text
稳定 ST 内容
→ 客户端本次实际消息，包括已有工具结果
→ 本 wake 固定的动态 ST 内容
→ 适用时追加本次来源说明与短期交接
```

v2 固定并验证 ST 自己的上下文帧，但不再把 v1 的逐字历史冻结条件套给整个客户端输入。客户端实际文字仍按当前内容传递；工具目录、参数、调用 ID、执行绑定和结果血缘检查继续保留。

它解决的是“ST 动态资料挡在长历史前面”的问题，**不会自动修复前端在最前面反复改写系统提示的行为**。同一工具轮中 ST 材料保持固定；下一次真实唤醒可以重新选择需要的记忆，不必为了缓存停用新记忆。

尾部动态帧会随着客户端消息增加而后移，因此“上一请求全文是下一请求完整前缀”并不成立。正确说法是：更长的稳定历史有机会复用，而不是整个请求永远不变。

### 2.4 实际观察与承诺边界

长期自用中，使用者已明确反馈 v2 的缓存表现改善。一次连续长窗口记录中，三次输入分别约为 74.2 万、74.5 万、75.0 万 token，按各次用量计算的命中率约为 **9.38%、99.33%、99.10%**。

这组匿名数字说明：在该次实际环境中，接近 75 万 token 的网关长窗可以出现高命中；第一条低、后续高，也说明不能拿单轮代表全部体验。它们不是受控 benchmark，不是 v2 相对其他方案的因果收益，不证明第一条低命中的唯一原因，不构成对其他用户的保证。

历史短供应商探针主要验证协议兼容，输入太短且命中为零，不能拿来证明省费。旧混合日志也不能直接拼成“优化前后提升百分比”。长工具输出缓冲预算的修复解决工具参数传递问题，**不是缓存命中修复**。

最近长期自用反馈为“命中率稳定约 **96%**”。这是使用者的观察，不是本次重新采样的全量账单统计，也不作为最低保证或新补丁的效果证明。下面第 8 节的 96–99% 来自另一位用户的自定义改法，两组反馈不能合并成同一实验。

### 2.5 一路修下来的经验

| 当时遇到的问题 | 采用的处理或得到的经验 | 现在怎样用 |
| --- | --- | --- |
| ST 动态资料放在长历史前面 | 把稳定与动态材料拆开，采用尾部布局 | 先核对 v2 实际生效，不仅看配置文件 |
| v1 严格冻结整个客户端历史，遇到续轮重新展开状态 | v2 只固定并认证 ST 帧，继续保留真实客户端消息与工具校验 | 不把 409 当缓存问题，也不把新电量、时间偷偷改回旧值 |
| 源码升级了，私有配置仍沿用旧值 | 源码默认与新安装模板不是一回事 | 查服务真正加载的配置，配套升级组件，完成旧轮后验证新轮 |
| 首轮低，连续长窗后来高 | 单次请求不足以判断长期表现 | 对齐输入规模、间隔、普通轮和工具续轮，再统计 |
| 工具描述、提醒或历史重建影响输入 | 固定不应变化的快照，真正更新的内容仍须生效 | 不以过时工具合同或过期记忆换取命中 |
| 日志显示客户端前缀保留，用户仍低命中 | 分段观测不能证明最终发给上游的整体结构 | 使用最终请求的本机有限差分，见第 8.4 节 |
| 用户已经启用 v2，角色改法后改善 | 收录为具体线路的兼容线索，尚非公版通用修复 | 见第 8.3 节；不要只改一处角色或取消校验 |

前两项的实现与回归入口列在第 10 节。经验的核心不是“把所有内容都移到后面”，而是**稳定的内容尽量保持稳定，当前事实及时更新，工具和授权仍然正确**。

## 3. 第一步：确认改的是正在运行的配置

### 3.1 确认自己的启动方式

先记下：ST 版本或 commit、前端名称与版本、启动时使用的源码目录、实例私有配置的位置、上游实际模型。不要截图或粘贴整份配置。

- **本仓库安装向导用户**：找到安装完成时给出的启动命令及其私有安装目录，使用该实例的 `config.env`。保留向导使用的源码位置；不要以为解压了新源码就自动更新旧服务。
- **手工前台启动用户**：核对实际启动命令的 `--config` 路径。
- **自建 systemd、容器或受管服务用户**：核对服务真正加载的配置文件、工作目录及环境来源。终端里临时设置的变量，不一定传进已运行的服务。

若一台机器有多个实例、多个模型路由，必须核对本次客户端究竟连到了哪一个。客户端显示名称可以是别名；它不一定等于真实上游模型 ID。

### 3.2 精确设置布局

在该实例私有配置中设置这一行：

```dotenv
STBRAIN_GATEWAY_CONTEXT_LAYOUT=tail-context-v2
```

使用精确小写值，不加多余空格或引号，不重复定义同一个键。不要修改 Key、owner/model 身份、数据库路径或执行 epoch 来“刷新缓存”。

| 情况 | 实际行为 |
| --- | --- |
| 新配置从当前 `.env.example` 创建 | 模板已选择 v2；仍需核对运行实例 |
| 旧配置没有这一项 | 源码默认仍是 `legacy`，升级代码不会替你改私有配置 |
| 显式设置 `legacy` | 保留旧布局 |
| 显式设置 `anchored-v1` | 使用 v1，不等于 v2 |
| 大小写、拼写或值不支持 | 当前启动器拒绝，不应通过删除校验来启动 |

这是网关的配置项，不是聊天内容、模型请求 body 的字段或 MCP 工具参数。ST 网关、Control、runtime 与启动器需要使用配套代码，不要只替换 `server.py`。

### 3.3 安全检查、重启，再验证新请求

1. 等当前生成和工具执行完成。不要在结果未知时反复重发、强杀或清空队列。
2. 按自己的部署流程备份和维护；配置切换不要求删除记忆或回灌旧库。涉及跨版本数据库兼容时，按 [OPERATIONS](OPERATIONS.md) 检查，不能直接降级覆盖。
3. 使用本仓库配置格式的用户，可在源码根目录以该实例 Python 检查配置。以下路径是示例，需替换为自己的私有配置：

   ```powershell
   python -B scripts/stiller_ops.py check --config C:/stiller-private/stiller.env
   ```

   它不请求模型；`valid_components: 3` 只证明配置校验通过，不证明服务已启动或客户端已连对。
4. 按原启动方式完成受控重启。向导用户用其完整启动命令；Linux 受管实例先读 [服务维护说明](LINUX-SERVICE-MAINTENANCE.md)，不要把需要离线收尾的实例当成任意进程直接重启。
5. 发起一条新的、无隐私的普通消息，并检查这次成功准备请求的安全性能记录。实际布局应为：

   ```json
   {"context_layout":"stbrain-context-layout/2"}
   ```

日志里的协议名和配置值不同，这是正常的。`stbrain-context-layout/1` 是 v1；`legacy` 表示本次实际走旧布局；`unknown` 可能是请求尚未准备成功，不能据此判定布局已启用。

旧 Control 可能不返回 v2 bundle，此时网关只有校验 legacy 上下文成功后才回退。所以“文件里写了 v2”不等于“这一轮实际用了 v2”。遇到回退应核对组件版本和运行路径，不要移除哈希或鉴权检查。

## 4. 第二步：读取正确的 usage，而不是猜命中率

### 4.1 字段与公式

DeepSeek Chat Completions 的常用字段：

| 字段 | 含义 |
| --- | --- |
| `prompt_tokens` | 本次模型调用的输入 token |
| `prompt_cache_hit_tokens` | 输入中命中的 token |
| `prompt_cache_miss_tokens` | 输入中未命中的 token |
| `completion_tokens` | 输出 token，包含服务商计入其中的生成内容 |
| `prompt_tokens_details.cached_tokens` | 官方定义与 `prompt_cache_hit_tokens` 同义，不能重复相加 |

```text
完整性核对：prompt_tokens = hit_tokens + miss_tokens
单请求输入命中率：hit_tokens / prompt_tokens
同组输入加权命中率：sum(hit_tokens) / sum(prompt_tokens)
```

输出不放进命中率分母。输入为零时比例未定义；字段缺失时显示未知，不把缺失当 0。其他供应商或兼容代理可能使用不同字段，不能自动假定与 DeepSeek 相同。

例如三次输入为 10,000、10,000、1,000,000，命中为 9,000、9,000、0。前两次各 90%，但输入加权命中只有约 1.76%。简单平均三个百分比会严重误导费用判断。

### 4.2 ST 日志里看哪些字段

通过本仓库前台启动时，三个服务日志显示在启动终端；启动脚本不会额外保存一份日志文件。自建服务的日志位置由部署方式决定。不要为了排查把服务监听公开，或开启会记录请求 body/Authorization 的代理调试日志。

网关专用性能事件为 `gateway_request_performance` 或 `gateway_request_performance_failure`。正常日志只记录受控计数、时间与状态；**分享前仍须从混合日志中挑选字段，不上传整个终端输出**。

用于一轮检查的白名单：

```text
request_started_at_utc, request_finished_at_utc
model, model_is_known, continuation, context_layout
usage_observed, usage_snapshot, usage_snapshot_complete
usage_snapshot_consistent, usage_snapshot_invalid_fields
stable_context_bytes, dynamic_context_bytes
stable_context_changed, dynamic_context_changed, wire_tools_changed
client_input_prefix_preserved
stage, finish_reasons, http_status, upstream_status
```

优先使用同一条日志中的 `usage_snapshot`。当前实现不跨多个 SSE 事件拼出“看似完整”的四项计数；后续若只收到部分 usage，完整性可能变为 false。缺失或不一致应如实登记，不能手动补齐为某个漂亮比例。

以下是**合成示例，不是实际测量**：

```json
{
  "event": "gateway_request_performance",
  "context_layout": "stbrain-context-layout/2",
  "continuation": false,
  "usage_observed": true,
  "usage_snapshot": {
    "prompt_tokens": 10000,
    "completion_tokens": 300,
    "prompt_cache_hit_tokens": 9000,
    "prompt_cache_miss_tokens": 1000
  },
  "usage_snapshot_complete": true,
  "usage_snapshot_consistent": true
}
```

此请求的输入命中率为 90%，不是 `9000 / 10300`。日志中兼容保留的顶层旧计数不应与其他事件的计数混用。

### 4.3 批量统计、工具续轮和失败用量

- 同一条人类消息可能触发多次上游工具续轮。“API 请求数”不等于“人类说了几句话”。
- 批量汇总时按相同模型、时段、布局、普通请求/续轮分组；连接探针、标题生成等辅助请求与正常长窗分开。不要把它们的简单平均值当正常聊天命中率。
- 同时报告总输入、加权命中率、低命中请求数及输入规模。可以额外报告每请求比例中位数，但不能让它替代加权结果。
- 失败也可能已经消耗上游用量。HTTP 失败、正文为空或客户端断开，不等于免费；没有 usage 则计费未知，以供应商账单核对。
- 窄条件的空正文恢复如果实际发生，会另记 `gateway_empty_completion_recovery`，包含 `attempt_count`、`usage_attempts`、`usage_total`、`usage_complete`。普通 usage 描述当前模型调用，不自动等于所有尝试的费用。按实际尝试统计一次，不能再把 `usage_total` 与已逐项累计的尝试相加。
- 对照费用时还需对齐模型、计价时期、时区、命中/未命中输入与输出。不能用“总费用÷总 token”反推缓存命中率，也不把价格变化当成命中率变化。

### 4.4 换供应商后不要照搬字段与规则

上面的四项完整性核对针对 DeepSeek Chat Completions。兼容 OpenAI 的地址，不等于具有相同缓存实现；其他供应商可能没有 `prompt_cache_miss_tokens`，不能因为缺这一项就认定它完全没缓存。

OpenAI Responses 可用 `usage.input_tokens_details.cached_tokens` 核对实际复用；其缓存要求匹配渲染后的前缀，工具及相关请求设置也会影响它。不同模型的最低长度、保留时间和可配置选项不同，应按实际模型查看 [OpenAI 缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching) 与 [用量诊断](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics)。这不是说 ST 当前网关会自动支持或透传其中所有新选项。

不要把别家的 `cache_control`、`prompt_cache_key` 或保留时间参数随意塞进 DeepSeek 请求；也不要把“缓存写入”算成“本次缓存读取命中”。先核对所用端点的官方字段定义，再决定怎样统计。

## 5. 第三步：理解变化信号的范围

| 信号 | 可以说明什么 | 不能据此认定什么 |
| --- | --- | --- |
| `stable_context_changed` | 可比较请求间，ST 稳定帧改变了 | 一定存在错误；作者真实修订可以合法改变它 |
| `dynamic_context_changed` | 当轮动态资料改变了 | 缓存一定失败；v2 正是将其放到尾部 |
| `wire_tools_changed` | 客户端实际 `tools/functions` 内容或数组顺序改变了 | 工具权限一定改变，或这就是低命中唯一原因 |
| `client_input_prefix_preserved` | 注入前客户端消息是否延续此前输入前缀 | 最终上游请求前缀相同、供应商已经命中 |

`null` 表示没有可用的比较结论，例如进程刚启动、切换线程、前后布局不可比较；不是“未变化”，也不是某项检测失败的同义词。

**特别注意：`client_input_prefix_preserved=true` 不是整段最终请求的证明。** ST 帧拼装后还可能追加来源与 handover；handover 的相对时间也可能变化。最终上游还涉及执行元数据投影及模型请求的其他字段。这些不全在该布尔值的覆盖范围内。

上述日志不是完整最终请求差分。源码提供的离线比较器只能分析你已经在本机保存的两份 JSON body；它不会替你抓包、读取运行中网关或证明供应商内部 token 前缀。用法与输出边界见 §8.4。仍有疑问时，应优先针对合成请求在最终组装与序列化处做有限差分，不公开完整请求。

## 6. 第四步：按低风险顺序定位变化来源

先保留现有配置，用一个无隐私测试窗口连续观察数轮。每次只改变一个条件，记录版本与条件；不必导出原长窗，也不要让陌生人远程读取自己的记忆库。

### 6.1 系统提示与动态占位符

检查客户端是否在请求前部每次填入当前秒数、电量、随机字符串、设备状态或动态扩展结果。新增内容若只需要表示当前状态，可由客户端开发者设计为独立、靠后的更新；不能擅自抹掉用户需要的事实。

客户端开发者可考虑在一个 GenerationRun 内冻结本来不应变化的配置快照，下一次真实用户消息再重新收集动态状态。不要为了冻结而重写已经签发的工具参数、结果或回执。

仅仅更换用户问题的话题，不应被解释为必然冷缓存。要看换话题有没有导致靠前资料变化，而不是让用户停止正常聊天。

### 6.2 历史截取、压缩、导入与分支

检查低命中前是否发生了：切换窗口、重新导入记录、修改早期消息、切换回复分支、改变“发送最近多少条”、自动压缩、删除中间消息、改变历史格式。

这些动作可能改变很早的位置。前端看上去仍是同一个聊天标题，不代表发送数组相同。把数千条历史导入新窗口后的第一轮当作冷启动观察更合适，不能要求其必然复用原渠道的缓存。

压缩仍可是一项有效的成本策略，但它与缓存优化不同：输入变少可能省钱，同时原长前缀不再匹配。不要把一次压缩后的低比例单独判为网关退化。

### 6.3 工具目录、描述与排列

检查是否刚开启/关闭 MCP、刷新目录、修改某项工具描述/Schema，或客户端每轮用不同顺序生成工具列表。语义上“还是那些工具”，不保证发送的内容相同。

ST 授权目录使用名称与 Schema 等信息判断可执行合同；缓存观察比较实际发送的工具列表。两者不是同一个概念。偏好或提醒描述真实更新时，新的工具说明应优先，不能为了缓存继续发过时授权或旧文案。

在合成测试中可以固定目录、顺序与描述，然后观察；不要把“关闭所有工具后命中高”直接写成面向用户的永久解决办法。

### 6.4 思考模型与工具消息协议

思考输出、最终正文、工具调用及工具结果需按上游协议保存和传递。不同思考模式或客户端可能改变发送结构；模式切换应作为独立变量记录。

但“思考很长”本身不证明输入缓存失效。思考通常属于输出用量和耗时问题；输入、缓存输入与输出额度要分开核对。不要以关闭思考、删除必需推理字段或强制不兼容 `tool_choice` 作为缓存通用修复。

若报 400、工具结果不匹配或正文生成失败，先修复协议兼容问题。一次根本未正常完成的请求，不适合作为正常命中率基准。

### 6.5 模型路由、账号与代理

检查客户端别名背后的上游实际模型、端点、账号、API 协议及第三方中转是否一致。不同路由即使显示同名，也不应假定共用缓存。

直连与网关做对照时，要记录其中不可避免的差异：网关增加 ST 内容，可能还涉及不同工具、头部与上下文布局。一次“直连高、网关低”是调查线索，不是已经识别了唯一根因。

供应商缓存不能通过清空 ST 数据库、换执行 epoch 或重新生成身份凭证来可靠“重建”。这些动作可能损坏业务状态，且不是缓存排查步骤。

### 6.6 冷缓存、短请求和超长请求

官方当前说明：缓存需要已持久化的完整前缀单元。请求边界、多个请求的共同前缀识别，以及长内容的固定间隔都会参与持久化；构建需要时间，闲置后会回收，属于尽力而为。

因此，`A+B` 后立刻请求 `A+C`，第二次可能不能复用已存在的完整 `A+B` 单元；系统识别出共同 `A` 后，后续 `A+D` 才可能复用 `A`。不要用“文本看起来大多相同”推导出“第二次必然全命中”。

- 短请求的百分比容易波动，固定提示与工具开销占比也可能较大；短探针不适合证明长窗节费效果。
- 长请求有更多潜在稳定内容，但一次靠前变化、压缩或冷启动的未命中成本也更大。
- 超长窗口应该记录实际输入 token、连续轮次与完整 usage；不能只用文件字节数、聊天条数或窗口百分比代替输入量。
- 长时间未使用、切模型或切路由后先观察数轮，不能要求第一轮复制先前的命中表现。

### 6.7 命中很高却仍然慢或贵

先分清卡在哪：发送长请求、等待首个输出、生成思考/正文、等待工具，还是前端渲染和 TTS。缓存比例不是端到端耗时指标。

- 缓存命中不等于请求体不再上传。手机网络、代理或中继上传慢，可能在模型开始处理前就花掉很长时间；先比较同一设备下短消息与长消息的发送耗时，不先改 ST 记忆算法。
- 输入命中高，也可能生成很多思考、正文，或多次工具续轮。把实际输出用量和全部上游调用计入费用。
- 新增大附件、图片帧或长工具结果会增大当前输入。即使命中量没减少，分母变大也会使比例下降；同时看“命中多少”和“新增多少”，不只看百分数。
- 压缩能减少后续输入，但会改变上下文。由使用者决定是否压缩并保留原记录；不要为保住旧缓存坚持发送不必要的超长上下文，也不要为了命中率关闭用户需要的屏幕共享。

**合成算例：**上轮输入 100,000、命中 96,000 是 96%；这轮仍命中 96,000，但新增材料使输入增至 120,000，比例就是 80%。这不能单凭比例判为“原来缓存丢了”。实际费用还要按模型当期输入、缓存输入与输出价格分别核算。

## 7. 快速判断表

按最符合的一行开始。“处理后核对”是验证方向，不是保证下一条必然高命中。

| 看到的现象 | 先核对 | 怎样处理 | 处理后核对 |
| --- | --- | --- | --- |
| 刚升级，仍每轮很低 | 日志是否为 `/2`，客户端连的是哪个实例 | 按第 3 节改实际私有配置并配套升级，不复制单个源文件 | 新请求布局、版本与运行路径一致 |
| 第一轮低，随后多轮高 | 是否长时间闲置、换模型、导入或刚压缩 | 先保留观察，不连续重启“清缓存” | 连续 usage 与总未命中量，不只挑最高的一轮 |
| 每轮只命中开头很小一段 | ST 稳定帧、前端前部、工具列表哪里最早变化 | 按第 5–6 节定位；前部稳定仍异常则查第 8 节 | 首差位置、完整 usage 和实际路由一起比较 |
| 每次工具刷新后低 | 内容、Schema、描述和数组顺序是否变了 | 无需变化的目录保持确定顺序；真正更新后允许新基线 | 不反复变动，工具仍正确执行 |
| 同一工具链中提示变化或 409 | 时间、电量占位符是否每步重算，是否仍用 v1 | 使用配套 v2，客户端按真实生成轮管理快照 | 新用户轮事实更新；工具续轮不改参数或伪造回执 |
| 编辑、切分支、压缩后突降 | 发送历史的起点与中间内容是否改变 | 保留正常操作，把变化后当作新基线观察 | 后续未继续修改的历史能否稳定复用 |
| 加附件或长工具结果后比例下降 | 命中 token 是下降了，还是输入分母变大 | 比较绝对数与新增内容；按需管理上下文 | 新内容正常读到，后续费用与用量可解释 |
| 短测试一直为零，长窗却正常 | 请求长度、供应商规则与测试用途 | 不用一句话探针外推长窗缓存，不堆无用文字刷比例 | 用日常同类请求作对照 |
| 换供应商、中转或账号后下降 | 实际模型、端点、缓存字段及路由 | 分组统计，核对官方规则；不假定跨线路共用缓存 | 同一路由的连续请求结果 |
| 前缀保留标志为 true，仍低 | 标志只覆盖客户端输入，不覆盖全部最终请求 | 本机比较最终消息结构，必要时提供安全摘要 | 不把字节相同当供应商内部 token/落盘证明 |
| 尾部动态 system 有时出现，有时没有 | 当轮是否确实没有召回、角色是否有线路兼容问题 | 见第 8 节；不填假记忆或保留过期记忆 | 准确区分公版机制与用户自定义改法 |
| 工具续轮 400、空正文或循环重试 | 错误类型、角色、推理字段与调用/结果配对 | 先停止重复重发，修协议再讨论缓存 | 正常完成一轮，无重复执行，无新增协议错误 |
| 窗口显示 75%，缓存显示 10% | 两个数字的分母 | 按第 1、4 节分别理解，不调整记忆库 | 用量记录与公式对应 |
| usage 缺失、不完整或不一致 | 是否流被截断、代理漏传或 UI 未展示 | 标为未知，核对供应商记录 | 不补造统计、不将未知当零费用 |
| 命中 96% 仍很慢或贵 | 上传、生成、工具、输出量与总调用数 | 按第 6.7 节分段定位 | 看总耗时与实际费用，不只看比例 |

### 一次排查怎样才算结束

把“改了什么”和“改后有什么证据”写在一起：相同版本/模型/线路下，布局符合预期、普通回复与工具续轮均正常、已有连续用量不再出现同一异常；若做了额外付费测试，记录其次数和费用范围。最好保留一组之后的日常观察，别因单轮 99% 就关闭所有低命中反馈。

若两轮对照改变了模型、前端、注入角色、工具数量四个因素，只能说组合方案改善，不能把功劳全部算到其中一个参数。无法解释的现场继续保留，不要求用户用“聊天内容不对”来解释。

## 8. 已启用 v2 仍低命中的用户案例

[Issue #1](https://github.com/AZHi-xinxin/StillerBrain/issues/1) 的原反馈已经启用 `tail-context-v2`。因此，“打开 v2”不是对该现场的完整答案；开发者本地长窗高命中、工具流缓冲修复或增加这篇指南，也都不能证明它已修复。

### 8.1 作者已经补充的新证据

作者在 2026-09-29 的首份对照中使用 preview.1、RikkaHub、DeepSeek V4 Pro 官方直连上游，并报告四次请求间隔约 17.4、18.2、27 秒。随后在 **2026-09-30 07:17:00 UTC** 更正计量单位，**08:40:30 UTC** 再次补充相同内容：先前的 82,644 / 79,071 / 79,878 / 79,339 与 55,741 是 UTF-8 解码后的**字符计数**，不是字节计数。该组最终 body 的实际 UTF-8 大小为 **141,128 / 136,873 / 138,032 / 137,363 字节**，首个不同字节的位置为 **108,711**。请勿继续引用旧数字作为字节证据，也不能直接把其中任一种长度换算成 token。来源：[作者更正与补充](https://github.com/AZHi-xinxin/StillerBrain/issues/1#issuecomment-5907493368)。

作者报告前段历史内容及模型、生成参数、工具列表保持相同，差异在后段，但命中输入仍约为 **1,280 token**。这是命中量，不是未命中量。关于消息范围，首份报告写 `messages[0..48]`，更正帖称前 48 条；维护者没有收到原抓包逐项核验，本文不将这两个计数表述合并成已独立确认的精确索引。

这些是**作者的现场取证报告，尚未由维护者独立复现**。它们已经缩小调查范围：不能继续只要求作者检查“前部历史是否每轮变化”，也不能继续将一般性的前缀破坏猜想当作该现场的既定根因。

同时，JSON body 的共同字节前缀，不等于供应商内部序列化后的 token 前缀，更不等于已经持久化且可复用的缓存单元。暂不能据此断定是供应商故障，或证明网关其他部分完全无关。

### 8.2 哪些问题已回答，哪些仍待证明

不再把“有没有启用 v2”“请求头是否随轮次变化”“动态消息为何有时不存在”列为作者尚未回答的问题。更正帖已说明：

- 配置和运行日志均确认 v2，无 legacy 记录。
- 作者检查到应用设置的三个头以及 HTTP 客户端默认头跨请求稳定；长度头只跟随 body 大小改变。其部署未另配代理或 CA。原评论同时保留了边界：尚可另查真正的 wire 层，不能将配置/代码层检查写成已完成全部链路抓包。无需公开任何头部值。
- 四次请求的总消息数依次为 50 / 51 / 54 / 55；尾条依次为 system / user / system / user。两条 system 内容长 3,298 / 616 **字符**，对应情感召回 10 / 1 条。作者说明没有召回且其他动态层也为空时，该尾条被省略。这是数据条件导致的确定行为，不是随机丢消息。

当前源码也支持最后一项机制：[runtime/onboarding.py 的 `_context_bundle`](../runtime/onboarding.py) 只在动态集合非空时构造该帧；[rikkahub_gateway/server.py 的 `upstream_headers`](../rikkahub_gateway/server.py) 为普通上游路径设置固定名称的三个应用头。代码能解释自身分支，但不能代替作者实际部署的完整 HTTP 传输证据，也不能证明所有托管路由行为相同。

**尾部内容或消息数量改变，能够解释尾部不再相同；仅凭上述字节对照，还不能解释为什么长前段只命中约 1,280 token。** 作者随后提供了角色修改后改善的反馈，见第 8.3 节。这使角色兼容成为值得验证的线索，但不是全局关闭情感记忆、填充假召回或保留过期注入的理由。

剩余调查应先复用现有证据：对齐每个最终请求与该请求的完整 usage、时间及实际上游路由；区分原始 UTF-8 body 比较、解析后的消息结构比较和供应商内部的输入序列。若需要进一步控制变量，优先合成内容、固定配置和少量连续请求，只变一个因素；没有新的安全证据需求时，不让作者重复提交同一轮头部/召回说明，也不让其反复重发昂贵长窗。

本版本已有分段观测，尚不能由一个布尔字段证明整个上游前缀。`client_input_prefix_preserved` 的覆盖范围与作者直接比对最终 body 也不同，应分别记录。移除来源/交接尾注后改善可以作为线索，但没有独立控制变量和完整证据前，不能把它定为唯一根因。

本说明不宣称该工单已关闭，也不将缓存未命中视为用户使用方式错误。后续结论以工单中的实际复现及修复证据为准。

### 8.3 后续反馈 动态记忆改用 user 角色后改善

作者于 **2026-10-03** 补充：其自定义部署将动态记忆由 `system` 改为尾部 `user`，稳定身份块仍保留 `system`，报告命中恢复到 **96–99%**。作者还报告中间尝试 `assistant` 角色曾触发 `reasoning_content must be passed back`，伴随重复重试，最终回滚该尝试。来源：[Issue #1 后续修法](https://github.com/AZHi-xinxin/StillerBrain/issues/1#issuecomment-5972431749)。

这是重要的现场改善反馈，不应再写成“用户一直没有找到任何改善办法”。但要分清三件事：

1. **用户自己的部署：**作者报告已改善；我们未取得其最终补丁与完整对照独立复验，不将评论中的根因归纳扩大为所有 DeepSeek 请求的普遍规律。JSON body 中的位置与模型服务最终怎样组织 system 内容也不能直接画等号。
2. **当前公版：**核对 `0.2.0-preview.5`，`runtime/onboarding.py::_context_bundle` 的动态帧仍为 `system`；网关 `_injected_message` 仍只接受 `system`。**公版没有 `DYNAMIC_CONTEXT_ROLE` 配置项**，把这个名字写进环境文件不会启用该方案；只改运行时会被网关拒绝。
3. **后续适配：**2026-10-10 核对时工单仍 open。这次教程更新没有合入角色补丁，不代表公版已经对该现场完成修复。

普通用户：如果第 3 节已经确认 v2、连续请求仍异常，按第 9 节提供脱敏用量与版本，并指出是否符合这个案例。不要求你自行替换源码，更不要直接删掉角色、哈希或身份校验。

开发者要验证这条线索，应在隔离环境先检查以下项目，再决定是否提交适配：

- 将角色视为协议变化，而不只是缓存开关：动态帧产生、网关校验、上下文哈希/绑定、尾注与最终序列化一起审查；稳定身份和硬规则不能跟着整体降级。
- 宿主注入的资料必须仍标明是记忆参考，不能被记成“人类刚刚亲口说的话”；确认不会被客户端或服务误判为新用户轮，不会重放旧工具。
- 使用合成材料，只改变动态角色一个条件，保持模型、历史、工具目录、路由和间隔尽量一致；记录是否存在动态帧、最终角色及完整 usage，不上传原私聊。
- 回归普通回复、零召回、工具续轮、思考模式、多个 system、短期交接、停止/重试和权限负控。遇到 400 先停止重试并撤回实验，不伪造 `reasoning_content` 或工具结果。
- 拿到可复验的兼容和效果证据，再安排配套发布。不能为了一个线路的比例全局改变其他模型的消息语义。

### 8.4 可选 只在本机比较已保存的两个最终请求

若你已经自行保存了脱敏或合成的**最终上游 JSON body**，可在源码根目录运行：

```text
python scripts/compare_final_payloads.py first-request.json second-request.json
```

此工具不抓包、不联网、不重放请求、不读取配置/数据库，也不创建文件。它只读这两个明确指定的文件，单个限 16 MiB；拒绝无效 UTF-8、重复 JSON 键、非有限数值和不合要求的消息结构。输出仅含固定字段名、长度/计数、固定角色类别、布尔差异和错误代码，不输出请求正文、文件路径、字段值、Token、工具参数或内容摘要指纹。

- `raw_bodies` 将 UTF-8 **字节数**与 Unicode **码点数**分别报告；码点数也不等于界面可见字符数或 token 数。
- `raw_comparison.common_prefix_utf8_bytes` 是两个原始文件的共同字节前缀长度；`first_difference_utf8_byte` 是从 0 开始的首差位置，完全相同则为 `null`。一份是另一份的严格前缀时，位置为较短文件长度。
- `message_comparison.common_prefix_messages` 在解析 JSON 后比较完整消息对象；保留数组顺序、忽略对象键的书写顺序。它和原始 body 字节前缀是两个指标，不得混为一谈。
- `known_fields` 只比较固定的模型、参数和工具字段是否存在/相同，不显示值；不会枚举请求中自定义字段的名称。
- 这些结果只证明**所提供文件**的差异，不能证明文件确实位于最终出口、隐藏路由未变、供应商收到相同 token 前缀或缓存已经持久化，也不输出“命中率已修复”的结论。

完整请求文件仍可能非常敏感，即使工具输出没有正文也不应上传原件。只按需分享上述有限输出；未保存最终 body 时，不需要为了填反馈模板额外导出真实私聊。
