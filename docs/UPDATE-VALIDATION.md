### Linux 实际系统调用补验

在独立 Ubuntu 24.04 x64／WSL1、CPython 3.12.3、glibc 2.39 中，将候选源码和临时状态复制到私有 Linux 文件系统，运行以下针对性测试：

- 手机引导、标准安装器与已有运维行为；
- 真实 SIGTERM／SIGHUP、部分启动失败、原信号处理恢复及不终止无关合成进程；
- 实际私有权限、文件和目录同步、原子替换、SQLite WAL／重开完整性；
- 异进程文件锁排他／释放、符号链接拒绝及探针清理边界。

共 **163 项全部通过，无跳过**。关键测试源码按 LF 规范化后与冻结候选一致。该范围不是完整 Linux 服务回归、真实模型请求或手机 PRoot 运行证明。验证环境已停止，未启动或改动既有生产环境。

### ARM64 依赖证据与未通过的仿真环节

新增 30 项 ARM64 锁，完整保留原 Linux x64 的精确版本。25 个纯 Python wheel 不变，5 项本机代码依赖使用同版本官方 aarch64 文件。逐个核对官方 PyPI 来源、大小、SHA-256、内部名称与版本、Python／ABI／平台标签及目标依赖闭包。

已按完整哈希锁把 30 个 wheel 安装到隔离 ARM64 目标目录，并核查其中 12 个原生 ELF 的 AArch64 架构。**这是分发物验证，不是原生扩展运行通过。** 本机 WSL1／QEMU 尝试能执行 ARM64 的 `uname`，但在启动 CPython 前遇到地址映射失败；该环境中的 PRoot 也未能正常运行。因此没有完成 ARM64 Python、5 项原生依赖导入或 ST 三服务运行验证，不据此判断真实 Android 支持或不支持。

[ARM64 清单](dependency-inventory-linux-arm64-py312.json)及[依赖说明](DEPENDENCIES.md)提供可复核来源。此轮没有新的完整漏洞审计，也不把过去的 OSV 回执当成今日结果。

### 代码审阅、包装与上线边界

独立审阅发现并修复新版 Termux Python 将系统名报告为 `Android` 而被旧门槛误拒的问题，已补调用实际宿主判断函数的正反测试。ST 本体仍只安装到满足 glibc／CPython 条件的客体中，不放松原生 Bionic、共享存储或哈希限制。

公开文件集合不包含私有配置、数据库、附件、日志、venv、wheelhouse 或 Ubuntu rootfs。源码归档由完整 manifest 验证；候选 ZIP 另做文件集合、CRC、逐字节及 SHA-256 检查。模式扫描发现的新凭证样式是明确的合成测试字符串；模式扫描不构成全部 Git 历史隐私认证。
