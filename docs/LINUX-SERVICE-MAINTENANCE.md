# Linux 服务维护：系统更新与 ST 重启

[安装指南](INSTALL.md) · [启动、备份与导出](OPERATIONS.md)

## 先分清是谁重启了什么

ST 托管在 Linux VPS 时，“系统更新重启了服务”通常指 **VPS 的 Linux 系统更新后重启某个后台服务**，不代表手机、家中电脑或整台 VPS 重启。若仅重新启动了 ST 进程，VPS 的开机运行时间并不会归零。

Ubuntu 24.04 的 `needrestart` 会在 APT 更新后重启受影响的服务，非交互式自动更新也可能触发。它不会自动理解部署者为 ST 增加的停服证明、执行批次收尾或备份步骤。机制与单服务例外见 [Ubuntu 官方说明](https://discourse.ubuntu.com/t/needrestart-changes-in-ubuntu-24-04-service-restarts/44671)。

## 哪种安装需要关注

| 当前运行方式 | 本页如何适用 |
| --- | --- |
| 公版安装向导 / `scripts/stiller_ops.py start` | 当前为前台运行，不自动安装 systemd unit 或 `needrestart` 配置。按原启动入口正常停止；不要为了照抄本页创建服务或排除规则。 |
| 部署者另行配置的 systemd 服务 | 核对该实例的真实服务名、停止方式和重新启动契约，再决定是否需要单服务例外。 |
| 带离线收尾收据的受管部署 | 普通“停止后立即启动”可能不满足启动条件；必须使用该部署已有的受控维护流程。 |

本公版源码**不包含私人 VPS 的 `linux_supervisor.py`、`linux_offline_finalize.py` 或通用的生产离线收尾命令**。不能从其他实例复制状态文件、收据或 epoch，也不能把不存在的私有脚本当成本仓库安装步骤。

## 服务端停机可能看起来像“模型一直不回复”

一次已恢复的 Ubuntu VPS 实例故障中，自动更新后的维护程序直接重启了 ST。旧监督器正常停止，但新启动所需的本轮离线收尾收据尚未生成，服务因此拒绝启动。对外 HTTPS 代理仍在监听，实际后台却不在了。

这是服务生命周期与自动维护流程的兼容问题，不等于模型余额耗尽、记忆丢失或所有慢回复都来自网络。端口打开、模型清单存在、健康接口成功和真实生成成功也是不同层次的证据。不同代理和客户端可能表现为等待、断开或报错，不能保证某一种 UI 提示。

维护者先以实际服务名检查状态、退出时间与更新日志，不连续重发用户消息：

```sh
# 仅当实际部署的服务确实叫 stillerbrain.service 时使用；否则替换为真实名称。
systemctl show stillerbrain.service --property=ActiveState,SubState,MainPID,Result,ExecMainStartTimestamp,ExecMainExitTimestamp
journalctl -u stillerbrain.service --since '2 hours ago' --no-pager
```

日志可能含私人信息，只在受信终端查看并脱敏后分享；不要输出完整环境变量、凭证配置或聊天正文。结合 APT / unattended-upgrades 的更新记录区分“应用崩溃”和“被维护程序重启”。

## 可选：只排除不兼容普通重启的那一个服务

**仅供已经配置 systemd 服务、且已确认它需要额外安全收尾的维护者使用。** 优先让部署具有经过验证的受控维护流程；不要给所有安装默认关闭自动重启。

如果真实服务名就是 `stillerbrain.service`，并确认当地 `needrestart` 加载 `/etc/needrestart/conf.d/*.conf`，可在该目录新建一个专用 `.conf` 文件，内容如下；已有同名文件须先核查，不覆盖他人配置：

```perl
$nrconf{override_rc}->{qr(^stillerbrain\.service$)} = 0;
```

服务名不同就按实际名称写精确规则，转义名称中的点；不要改成匹配所有服务的通配规则。文件由 root 管理、其他用户不可写。核对现有规则没有冲突，实际匹配结果应仅将目标服务排除，不影响其他服务或近似名称。

这只是要求 **`needrestart` 不自动直接重启这一项服务**，不是关闭 APT、安全更新或系统更新，也不是保证任何程序都不能重启它。可使用 `sudo needrestart -r l` 进行只列表检查，不为验收运行真正的自动升级或 `-r a`。工具仍可能列出该服务需要维护；“被列出”不等于“仍会直接自动重启”。

**安全更新后仍需安排受控重启，以使进程加载已修补的库。** 例外不能成为永久不维护的理由；该规则也不覆盖管理员手动重启、其他软件包脚本、关机或整机重启。撤销规则前先验证该部署已兼容对应的重启方式，否则故障可能再次发生。

## 已停机时的恢复边界

由熟悉该部署的维护者按现有契约处理，而不是让模型猜命令或让用户删除状态文件：

1. 确认是哪个实例、哪三个组件和哪些数据库，保存服务状态、退出原因与配置位置；不要公开凭证值。
2. 确认旧进程及其他写入者均已停止；如果维护工具的独占端口检查会与 HTTPS 代理监听冲突，先由维护者保存并临时停用**对应路由**。只处理本实例，恢复时核对原配置，不关闭其他服务的远程入口。
3. 保留配置与三个数据库的一致性备份并检查完整性；不清空聊天或记忆库。
4. 对有执行生命周期约束的部署，使用它已验证的离线收尾入口，生成属于**准确旧运行批次**的真实收据，并验证业务内容未被改动。没有该入口或证据不足时先停下，不伪造收据、改写 epoch 或重新初始化来绕过。
5. 按原部署方式重新启动，核验后台健康、鉴权后的模型清单和 MCP 目录，再验证客户端 HTTPS 与一条受控真实生成。恢复路由后，用户结束挂起请求、重连 MCP，从一条新消息复测；不自动重做结果未知的工具写入。

不要把 `Restart=always`、重复 `systemctl restart`、无条件启动时收尾或复制其他批次收据当作修复。自动恢复必须另行设计、测试旧进程停止证明、准确批次收尾与失败退出边界；本次文档补充没有新增自动恢复器。

## 本次验证范围

2026-09-18 的实例恢复已验证三库备份、业务内容不变、后台健康、7 项日常 MCP 目录、远程 HTTPS 与一次短生成；使用者随后确认真实对话恢复。单服务配置在该实例的 Ubuntu 24.04 / `needrestart 3.6-7ubuntu4.5` 上验证了加载、精确匹配、其他规则不变和只列表检查。

这些是一个既有实例的恢复与配置验证，不是公版新增了同一监督器，也不代表所有 Linux 安装方式、整机重启或长上下文网络延迟都已验证。本次只发布通用运维说明，不带私人地址、配置、日志、密钥、数据库或恢复脚本；记忆运行时代码与版本保持不变。
